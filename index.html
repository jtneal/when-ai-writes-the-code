But I don't think we should build our understanding of AI around what it can't do today.

So what does all of this mean in practice?

I don't think we need to throw away the engineering principles we've spent years developing.

And I don't think we need an entirely new definition of software quality.

But I do think we need to become more deliberate about a few things.

[Advance]

First, we need to spend more energy understanding the problem before we start generating solutions.

This is something we've always said is important.

But now that implementation is so fast, the temptation to jump straight into building something is even greater.

Instead of immediately asking AI to implement a feature, we should be asking whether we fully understand the requirements.

What problem are we actually trying to solve?

What assumptions are we making?

What systems does this affect?

What would make this solution successful beyond simply passing its tests?

We can absolutely use AI to help answer those questions.

In fact, I think that's one of the best uses of the technology.

But the important point is that we don't skip the thinking just because implementation has become easier.

[Advance]

Second, we need to evaluate changes at the system level, not just the code level.

Our traditional code-quality practices remain important.

But readable code with good test coverage isn't enough if the implementation introduces unnecessary coupling or violates an important architectural boundary.

When we're reviewing changes, we should be thinking about the effect on the system.

Not just whether the new code looks clean.

And I think AI can help us with that too, especially when we give it meaningful context about our architecture and constraints.

[Advance]

Third, we need to get better at distinguishing evidence from confidence.

A confident explanation is not proof.

An AI-generated test suite is not automatically proof that we've tested the right behaviors.

And a successful build doesn't tell us whether we implemented the correct requirement.

We need validation that is appropriate for the risks of the change.

Sometimes that means more comprehensive tests.

Sometimes it means checking an architectural decision.

Sometimes it means confirming an assumption with another team or a business stakeholder.

The important thing is knowing what we're actually trying to establish, and gathering evidence that supports it.

[Advance]

And finally, we need to protect the development of engineering judgment.

That applies to everyone, not just junior engineers.

We should be able to explain why a solution was chosen.

We should be able to discuss the alternatives.

We should understand the tradeoffs.

And when something goes wrong, we should use that experience to improve how we approach similar problems in the future.

None of that requires us to stop using AI.

It requires us to be thoughtful about which responsibilities we're delegating and which responsibilities we're developing.
